### The loop
```
TASK -> implementer (own worktree) -> reviewer -> FAIL? -> same implementer fixes -> same reviewer re-reviews
                                              PASS -> merge main -> gate -> push -> PR -> CI -> UI validation -> merge
```

### Who does what
| Action | Orchestrator | Implementer | Reviewer | User |
|---|---|---|---|---|
| Write TASKs, create branches and worktrees | yes | no | no | — |
| Commit on its branch | yes | yes | no | — |
| Push a branch, open a PR | yes | no | no | — |
| Merge a PR that meets the merge policy | yes | no | no | — |
| Push to `main`, force-push, delete branches or worktrees | never | never | never | yes |

Anything not listed is not permitted by default.

### Branches and worktrees
- One branch per topic: `<type>/<topic>`, English. Types: `feat`, `fix`, `improve`, `refactor`, `perf`, `test`, `chore`, `build`, `docs`, `spike`.
- One branch, one worktree (at `worktree_root`), one implementer. Two branches that touch the same files never run in parallel.
- Each new worktree runs `worktree_setup` before the first commit.
- `TASK-*.md` and `REPORT*.md` are untracked (gitignored), and so is `.build-slot`.

### Commands
Full gate (reviewer and orchestrator):
```sh
sh scripts/gate.sh
```
Branch checks (implementer, crates touched only):
```sh
cargo fmt --all -- --check
sh scripts/build-lock.sh cargo check -p <crates> --all-targets
sh scripts/build-lock.sh cargo test -p <crates>
```

### Merge policy

**A PR merges only when all hold:**
- Implemented, tested and working: the full gate passed after merging the current `main` into the branch.
- The reviewer gave PASS on the final commits. Any commit after a PASS needs a new PASS, except a merge of `main` with no conflict resolution.
- Extra required reviews passed: `/security-review` (Claude Code) on branches touching network, authentication, input injection, file transfer, the Windows service or the installer.
- CI is green on every job.
- The feature was validated through its interface (`ui_validation`), with evidence. If there is no interface, the PR states `n/a` and why.

A criterion that does not apply counts as met only when the PR says so and why.

**Who merges:** orchestrator. Command: `gh pr merge <n> --merge`. Never `--delete-branch`, never squash unless the project says so.

**Review rounds:** after 3 failed rounds on a branch, stop and ask the user.

**Branches:**
- Never delete a branch or worktree. Cleanup is the user's call.
- Before rewriting any existing commit: `git branch backup/<branch>-before-rework`.
- Never force-push a pushed branch, and never push to `main` directly.

**Commits and PRs:**
- Commit messages: `type/short description`, one line, no body, in English.
- Attribution: none (no `Co-Authored-By` or "Generated with" trailers in commits or PRs).

**Stop and ask the user:**
- before anything they cannot undo: deleting, force-pushing, merging a PR that misses a criterion;
- before irreversible or external choices: licence, third-party binaries, publishing, paid services.

Record these as pending decisions in `REPORT.md`. Never work around them.

### Decisions taken on the way
Each branch records what it decided in `docs/decisions.md` (tracked), in a commit on the branch:
```
- `<type>/<topic>`: <decision>. <reason, one line>.
```
`REPORT.md` is the orchestrator's untracked running report, not the decisions log.
